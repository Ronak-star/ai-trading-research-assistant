# AI Usage Note

## Which AI tools were used

Claude (Anthropic) was used as the primary development assistant to scaffold and write this
prototype end-to-end: backend services, database models, API routes, frontend components, and
documentation. Sample market data was generated by a short deterministic Python script (fixed
random seed via `numpy`), not by an LLM.

## What they were used for

- Drafting the modular backend service pipeline (question parsing, missing-field detection,
  clarification merging, experiment building, validation, mock backtesting, result analysis,
  next-question generation) matching the required architecture.
- Writing the FastAPI routes, SQLModel schema, and Pydantic request/response types.
- Building the Next.js/TypeScript/Tailwind frontend: the ASK→CLARIFY→DEFINE→TEST→LEARN flow,
  step indicator, results dashboard with charts, and history/detail pages.
- Writing this documentation set (README, thinking note, this note).
- Running the app locally end-to-end (backend + a full API call sequence) to verify the flow
  actually works before calling it done, and running `npm run build` to catch TypeScript errors.

## Which decisions were made by the developer (acting as product/architecture owner in this session)

- The choice to default `AI_PROVIDER=mock` with a deterministic rule-based extractor, rather
  than requiring a live LLM key to run the demo at all — this was a deliberate product decision
  to keep the prototype reproducible and gradable offline, while keeping the OpenAI code path
  real and functional (not stubbed) for anyone who does supply a key.
- The decision to keep the backtest single-position/non-overlapping rather than attempting a
  more "realistic" portfolio simulation, to keep the demo within the explicit non-goal of "not
  a production-grade backtesting engine."
- The specific set of required-vs-optional missing fields (instrument, entry condition, holding
  period, test period) that gate whether clarification is shown at all.
- SQLite-by-default / Postgres-via-env-var, rather than hard-requiring a running Postgres
  instance, to balance the spec's requirement with ease of local evaluation.

## Which AI suggestions were modified/rejected

- An initial pass toward calling `create-next-app` to scaffold the frontend was abandoned in
  favor of hand-writing the Next.js project files directly, since it produced faster, more
  predictable results in this sandboxed environment.
- The equity-curve/backtest engine was kept intentionally simple (flat cost/slippage drag,
  non-overlapping trades) rather than the more elaborate position-sizing and intraday model
  that was initially considered, to stay aligned with the "small mock/sample engine, not
  production backtesting" requirement.

## What part of the implementation the developer is most proud of

The clean separation, enforced structurally (not just by convention), between **user-stated
facts**, **system assumptions**, **data-derived metrics**, and **AI interpretation** — each has
its own field in the database (`parsed_json` vs `assumptions_json` vs the numeric metric columns
vs `ai_conclusion`), its own visually distinct block in the UI, and its own service module in the
backend. That structural separation is the actual point of the product, and it's enforced
end-to-end rather than just described in a prompt.
